# 怎样试用，怎样判断值不值得留下

可以直接从这里试，也可以回到[中文入口](../00-先看这里.md)。先看[示范知识库](../示范知识库/总览.md)的具体成品，判断这种呈现是否接近自己想要的笔记。可用 Obsidian 把该子目录打开为独立库，或用普通 Markdown 阅读器查看；无需插件。打开时产生的本地配置不提交共享仓。

## 用一份材料试

没有知识库时，按[建立或接入路径](建立或接入个人知识库.md)完成首篇、位置、入口和追加方式；已有系统时试一个局部改进。不要求先建完整目录，也不把迁移当作默认步骤。

1. 把参考包放独立资料位置，选择允许处理的一份材料；AI 协助确定实际阅读位置，首次适配可先给预览再保存。已有库可用副本比较，原工程保持。
2. AI 简短了解记录方式与一个痛点；已说明的内容不再追问。
3. AI 判断该保留原文、局部优化还是提炼，先给实际技术内容预览和建议位置。
4. 你看过预览觉得有用，再指定可写位置，生成示范或授权局部合并；无法直接写入时由本人保存适合目标软件的内容。
5. 下次实际使用后判断是否更方便；有帮助再采用模板与必要存放约定。

如果材料、用途、可写位置已经明确，并且你已授权直接整理保存，AI 可以直接交付，不必重复等待一次预览确认。写完仍需核对关键事实、链接和范围。

已有文档清楚好用时可以不生成任何文件。首次试用也不要求造日报、学习计划、分工表或长接续提示。一个材料先做一个主要用途，不要求同时形成三篇。

## 能留下哪些自己的东西

| 情况 | 可以留下 |
| --- | --- |
| 没有知识库，材料很散 | 首篇有用内容、一个实际位置和必要阅读入口，后续再扩展 |
| 已有库但笔记难读 | 局部优化或更清楚的一篇示范，沿用原分类 |
| 经验总要重新查 | 保留具体步骤与证据的真实案例，关联必要知识 |
| 项目难继续 | 在原项目记录补实际进度与已决定的待办 |
| 原文已经好用 | 原文保留，最多补导航或有效关联 |

个人内容进自己的 Obsidian 或现有系统；源码、完整日志和波形留工程。本参考仓提供方法与更新，不能变成所有人的真实记录集合。自己建空目录和新对话试时，只提供本次材料；空目录不能保证模型没有历史记忆，仍明确限定本次输入。

## 真正验收成品

试着完成一个具体使用动作，而不是评价格式像不像专业报告：

- 找一个知识点，能否直接看懂例子和关键判断？
- 按经验记录操作，参数、步骤和必要错误信息是否齐全？
- 看项目记录，能否知道真实进度，而没有被附加新任务？
- 没有知识库的人能否找到首篇、从入口打开、知道下一次怎样追加？已有系统的改进能否融入原来的使用方式？
- 与自己喜欢的原笔记比较，具体例子、必要代码、依据与关联是否还在？关闭折叠时能否恢复主线，展开后能否读懂和查用？
- 位置和关联是否清楚？是否需要同时维护两篇相同事实？
- 是否还要不断回原文补核心内容，或绕过大量使用说明？
- 下次实际遇到问题时是否回来查用或补充？整理、核对与维护的总成本是否值得？

先整理一份，再完成一次之后的查用。记下具体卡点：哪里难懂、缺什么细节、是否愿意继续，不用文件数量代替效果。

## 权限与事实

只在使用者提供的范围读取和保存。目标文件不明确时先给预览，不回退到其他目录。合并到已有知识库前检查备份或版本与具体差异；本包提示不能技术性保证 Agent 不越界。未知证据保持未知，案例与示例不填成实测经历。

后续版本按有关改进选择采用，不整包覆盖个人库。工具和资料对照见[来源与取舍](已有方案与取舍.md)；[Obsidian 官方说明](https://obsidian.md/help/vault)用于核对库的操作。
